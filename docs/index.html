DroidXR

A new life for PSVR 2.
Your phone becomes the computer.

The goal is a phone-powered standalone and streaming PSVR 2 system: carry an Android phone with you, run VR from it, or use it to receive a wireless stream from a PC. Keep the headset. Change what powers the experience.

On the go Phone runs the experience → PSVR 2

PC streaming PC → wireless link → phone → PSVR 2

The intended setup. The headset still connects to the phone through a cable and suitable adapter; a fully portable power setup is part of the goal.

Working milestone: phone-hosted VR through Linux.
Current work: native Android. Worn-headset test unresolved.

How we got here ↓

01 / The reason for the project

I wanted to take the computer with me.

PSVR 2 already has hardware I want to keep: OLED displays and cameras for eye tracking. OLED pixels make their own light, which is useful for deep blacks. Eye tracking tells software where you are looking. The headset still needs a host computer to run the experience and make use of those features.

My idea is to make an Android phone that host. The phone would run the operating system and software for the connected headset. I want the freedom people look for in a Quest 3 or Steam Frame, while giving PSVR 2 a second life and making fuller use of the hardware already inside it.

There is a value argument too. Quest 3 uses LCD screens and has no eye tracking. OLED with eye tracking is available elsewhere, but it can be a four-figure headset purchase; Bigscreen Beyond 2e is one example in the US store checked in October 2026. I would rather explore what an existing PSVR 2 and a capable phone can become.

Competing with finished standalone headsets is the ambition. This remains a development project on a particular rooted phone. Features present in PSVR 2's hardware still need working software on each new route.

02 / Before VR, there was a display problem

First, make the phone send the right picture.

The first obstacle was getting control of the phone's external video output. Plugging in a display gives Android another screen, but VR needs the right image size, refresh rate and layout for the headset's two eyes.

We built an Android app to inspect that connection and manage the display setup. It reads what the connected screen says it supports, checks what the phone is actually using, and provides the controls for starting and stopping the experimental external-display path. The prototype uses a rooted RedMagic 11 Pro. Root access grants the project system access that a normal app does not have.

Part of the work involved DSC, or Display Stream Compression: reducing the image data sent across the video link. A phone-specific system module and display settings were part of the saved headset setup. A setting saying compression is enabled still needs to be checked against the real output. We also fixed a status check that could show an old display mode after the output had stopped.

That got us to a better question: once the output was available, which piece of software was allowed to control it?

03 / Giving the display to Linux

Android had to let go without losing its own screen.

The early route used a Linux container on the phone. A container is a Linux environment using the phone's existing processor and hardware. It let us work with desktop Linux graphics and VR software while Android continued running.

Linux needed control of the external output, and Android still needed its internal screen. Early attempts let both systems interfere with the same display resources. Some of those attempts froze or crashed the phone. Simply stopping Android's whole display system was unsuitable for a usable handheld setup.

The solution developed into a coordinated handoff. Android releases the external screen, a display lease gives the Linux client access to the required output resources, and stopping the session returns the output to Android. The app is the control point for this work. Cleanup matters because an old process or leftover connection can prevent the next session from starting.

With the handoff in place, a Linux desktop could lead toward a VR session. The next missing part was the software that understood the headset.

04 / Turning display output into VR

The picture and the tracking had to meet.

A VR runtime coordinates the application, the headset's movement and the images presented to each eye. We used Monado, an open source runtime. OpenXR is the common interface applications can use to request poses and submit their rendered views.

A pose describes where something is and which way it is facing. The image has to match the current head pose at the right time, or turning your head can feel wrong even while a game appears to be running.

The working container route also needed a compatibility bridge to Sony's Windows driver. That driver and its server were verified as x86-64, the processor format used by many PCs. The phone uses ARM64. Compatibility software handled those boundaries; the existing driver did not become native Android code just because the phone could run the whole setup.

This was built from existing open source projects, driver research and project-specific fixes. The important result was what happened when those pieces finally ran together.

05 / A game in the headset

Skyrim became visible. Then head movement became the test.

Skyrim VR ran through the phone's container setup, and I confirmed that it was visible inside PSVR 2. Both Sense controllers were switched on. At that first checkpoint, controller tracking and audio still needed their own checks.

Later, performance work exposed a problem a frame counter could hide. A game could report more frames while head turns still produced ghosting: old-looking images trailing the movement. The software doing the final headset update was waiting behind the game's graphics work.

We worked on how the phone scheduled those updates, how rendered frames were passed along, and how rendering effort could be concentrated near the direction of gaze. In a later recorded comparison, giving the headset update work real priority reduced its queue delay. I confirmed that the ghosting was gone, the controllers were fine, and motion felt much smoother in that test.

That gave us a working phone-hosted VR baseline and a lesson for everything after it: evaluate the picture while wearing the headset, as well as the numbers in the logs.

The motion result, with its limits

The 11 October project notes record a matched comparison in which compositor queue delay fell from about 7.7 ms to 0.48 ms. The game's completion-rate proxy fell from 58.5 to 39.3 frames per second, while the worn-headset report improved. These are results from that setup and comparison, not a general phone performance claim or a completed native Android result.

06 / Why one working game was not the finish

Alyx exposed another layer of compatibility.

Half-Life: Alyx used a different path: a native ARM64 Linux game, with its own bridge into the shared VR runtime. Reusing Skyrim's headset connection helped, but its game-side settings could not simply be copied across.

We worked through missing interfaces and graphics failures. Alyx eventually produced recognizable menu imagery, but the views were distorted, the hands were wrong, and I reported that it was unusable. A living process and a visible menu were progress; playable stereo still had to be solved.

That led to a SteamVR comparison. The normal download supplied PC-format binaries. A supplied Steam Frame recovery image contained the ARM64 runtime we were missing, so a separate SteamOS container was investigated. It started, but phone reboots made stability the priority. The next plan was to bring the needed runtime files back to the existing Linux setup instead of depending on the whole SteamOS environment.

Those experiments answered specific questions about the Linux route. They also made the next question more useful: how much of this could run directly in Android?

07 / The native Android route

Keep the phone. Remove the container dependency.

The next target is an Android runtime that talks to PSVR 2 directly. Native here means built for Android's own software environment, rather than relying on the Linux container and its Windows-driver compatibility path.

That means connecting the existing headset knowledge to Android's USB access, graphics output and application lifecycle. We can reuse open source work where it already solves a problem and study the remaining driver behavior where it does not. Copying a library from Linux is insufficient because Android expects a different set of system interfaces.

The early native checks opened the real headset, received status and motion-sensor data, and started an OpenXR session. Complete head-position updates were still not being accepted. Without usable view poses, that session could start and still submit no eye images.

A later unworn test moved forward: most full pose records were accepted, and it produced a two-view projection screenshot. The reported pose was marked VALID, with TRACKED clear. In plain language, it had usable reported data for that test without establishing active tracking.

Then I wore the headset for the next test. The output went black and every full pose packet was rejected. The worn-state decoder problem is still unresolved. The native route has a rendering checkpoint, but it has not reached working worn VR.

08 / Where that leaves the project

The destination is portable VR. The next step is a worn native scene.

The Linux-container route established phone-hosted VR in my setup. Native Android is in progress. The immediate job is to compare the unworn and worn data, fix the interpretation that rejects the worn records, and verify usable head poses and visible images together while the headset is being worn.

After that come the features that turn a test into something people can live with: reliable controller position and buttons, eye-tracking calibration, floor and room setup, recovery when tracking is lost, and repeatable start and stop from the app.

The longer-term goal has two routes. The phone can run compatible experiences itself, or receive VR streamed wirelessly from a PC and send the images to PSVR 2. Streaming still needs that working local headset runtime. Android app compatibility, supported phones, portable power, heat and battery life each need real testing.

I want this to become a practical alternative to buying another headset, with the freedom to choose what runs it. Giving PSVR 2 that second life is the reason for the project. Getting there means finishing the parts that are still failing.
