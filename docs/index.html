PSVR 2 / rooted Android / engineering journal

DroidXR

I'm working on getting PSVR 2 running from a rooted Android phone. This is the story of the working container path, the display and USB work behind it, and the native Android port still being built.

01 / How this started

Why I'm doing this

PSVR 2 was built around a console environment. A rooted Android phone has a different graphics stack, USB environment and runtime. Getting the two to work together means understanding those expectations and working through them.

There was skepticism about whether this could work. I kept going. The container-based phone VR path became a real milestone; now the work is about bringing the pieces together natively on Android.

02 / Display work

LinkDoctor, DSC and display handoff

LinkDoctor is where we've worked on inspecting the physical display path: EDID, native modes, display compression through DSC, and whether the reported output agrees with the active display state.

The earlier work also explored direct display handoff with DRM leasing, KMS and Vulkan. The difficult part is handing the external output to Linux while Android keeps its own screen working, then restoring that output when the session ends.

This is why the display work is more than finding a resolution that looks right. Ownership, synchronization and cleanup are part of making the path usable.

03 / Runtime work

Monado, OpenXR and the native runtime

An earlier checkpoint built Monado for ARM64 Linux with PSVR 2 and Sense support enabled. OpenXR and the graphics runtime are part of the work, alongside the display path.

The native Android effort still has its own integration work: USB probing, the external compositor, and the relationship between headset input and the runtime. I keep build results and hardware results separate in the project notes.

04 / Reverse engineering

Driver and tracking research

The driver research has included static analysis of the official driver and source inspection of the surrounding runtime. The useful questions are specific: what can be reused, what depends on another driver, and what has to be implemented for the native path?

USB interface behavior, device timestamps, calibration and Sense optical tracking remain important parts of that investigation. A changing input value is a useful observation; reliable pose and tracking need more evidence.

05 / Where it stands

Where it stands now

The container-based phone VR result is my reported milestone. The native Android port is still in progress, with device-specific integration and hardware checks remaining.

The next checks include USB transport and interface lifecycle, direct display acquisition and presentation, calibration, tracking behavior, and clean recovery when a device disconnects or a session ends.

Earlier engineering checkpoints came from the project notes. Current status here is supplied by the project author; this page does not read live headset or phone telemetry.
