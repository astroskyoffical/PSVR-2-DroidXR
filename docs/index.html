PSVR 2 / rooted Android / engineering journal

DroidXR

I want a rooted Android phone to run PSVR 2. The container-based phone VR path works. Getting the same project running natively on Android has been a much less cooperative exercise.

PSVR 2Rooted Android

Container-based phone VR: demonstrated.
Native Android: work in progress. Worn test unresolved.

01 / The goal

Why put a phone in the middle?

I wanted to find out how much of the host side a phone could take on: talking to the headset, running the XR software, and getting the right images onto the external display. That turns out to involve several systems which can each appear healthy while the headset remains completely black.

The working container path gave me a useful starting point. I could use a Linux environment on the phone and work with the runtime and graphics stack there. It also left a question worth pursuing: what would it take to make this a native Android application?

Native Android matters because I want that integration to belong in the Android environment: device access, application lifecycle, rendering and cleanup. It does not automatically promise better performance. It gives me a concrete set of dependencies to understand and replace where necessary.

02 / Finding the display

A mode list is the beginning

LinkDoctor is the display investigation tool in this project. I use it to inspect the display's EDID, its advertised modes, and the phone's display state. EDID tells me what the connected display reports that it can accept. I still have to establish what the phone is actually sending.

One earlier fix was about that distinction. DisplayPort debug information could retain an old mode after output had been disabled. The active-state check needed to compare the connector with the active display controller. A plausible-looking line in a debug dump was insufficient evidence that the output was running.

DSC, Display Stream Compression, is another part of this investigation. I need to understand the modes, compression capabilities and policy along the display path. A capability report or accepted setting alone cannot establish that compressed frames reached the headset correctly. The final check still has to include the physical output.

03 / Owning the output

The phone is already using its display stack

For the Linux route, the display work has involved DRM leasing, kernel mode setting and Vulkan. Here DRM means Direct Rendering Manager, the Linux graphics interface. The intended handoff gives the Linux client control of the external output while Android keeps its internal screen working.

That ownership has to last through presentation and end cleanly. A lease by itself does not stop the original display owner from changing resources that the external session depends on. Acquisition, synchronization and restoration all need to agree.

Earlier native pattern tests reached kernel commit and coordinated restoration. At that checkpoint, seeing the physical pattern still needed confirmation. Those results were useful for the display handoff; they did not establish headset output or validate every GPU buffer path.

04 / Connecting the runtime

Where Monado and OpenXR fit

OpenXR is the interface an application uses to talk to an XR runtime: request device state and poses, then submit rendered views. Monado is an open source runtime implementing that interface. It gives this project source code to inspect across the driver and compositor boundaries.

An earlier checkpoint built Monado for ARM64 Linux with PSVR 2 and Sense support enabled. That was a build result. Making the hardware work still required the USB, graphics and display paths to function together.

The Android port has its own integration work, including USB probing and the external compositor. A successful Linux build does not supply those Android connections by itself. I have to follow the data from the device through the runtime to the submitted frame, then check what actually appeared.

05 / Understanding the input

USB packets need an interpretation

The headset can send data before I have a correct explanation for it. Pose decoding means figuring out which fields are meaningful, their units and coordinate conventions, how device timestamps relate to runtime time, and what the status fields permit me to use.

Static analysis of the official driver and inspection of the runtime source help narrow those questions. They provide leads to test. They do not establish that a proposed interpretation behaves correctly on the phone.

Sense adds another distinction: controller input and orientation are separate work from optical position tracking. Having some controller data available does not complete that tracking pipeline. Calibration, transport behavior and recovery after a lost device remain part of the job.

06 / The recent native tests

The unworn result did not survive being worn

The native V2 test with the headset unworn was encouraging. The decoder accepted most of the full pose records, and the run produced a two-view projection screenshot. The reported pose state had VALID set and TRACKED clear.

That is a useful checkpoint with a specific limit. The screenshot establishes rendered views for that run. It does not establish what was visible through the lenses, or prove tracked native VR. In OpenXR, valid and tracked have distinct meanings; the reported valid state here cannot stand in for evidence of active tracking.

The subsequent worn test went black. Every full pose packet in that run was rejected. The worn-state decoder problem is still unresolved. Putting the headset on remains a fairly reasonable requirement for a VR system.

07 / Current status

Where it stands now

The container-based phone VR path works in my setup. Native Android remains in progress: there is an unworn projection checkpoint, followed by a failed worn run. I cannot call that working native VR, and it says nothing about compatibility with every phone.

The next immediate test is to compare the unworn and worn streams and find why the current decoder rejects the worn-state records. Then I need a worn run that demonstrates usable poses and visible projection together. Passing that would give the later calibration, tracking-loss, disconnect and session-cleanup checks a much firmer starting point.

That is the work I am documenting here: questions, bounded results, and the next experiment each result makes necessary.
